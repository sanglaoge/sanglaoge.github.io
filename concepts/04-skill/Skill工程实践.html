核心洞见

Skill 不是工具，是认知架构的一部分。操作型 Skill 教 Agent 完成一件事，认知型 Skill 改变 Agent 完成所有事的方式。

先摆清它和 Prompt 模板的分界，后面的工程账才有意义：

Prompt 模板Skill
性质用完即走的消耗品可规模化复用的认知资产
加载每次手动注入成为 Agent 认知环境的一部分
适合一次性任务持续运行的 AI 工作流

从模板到资产的演进：

阶段一
Prompt 模板

手动注入 · 用完即走

阶段二
单个 Skill

沉淀一个动作的完整打法

阶段三
Skill 工程

一群 Skill 的加载/触发/依赖一起管

不是所有能力都该做 Skill

判断标准只有一句：一个人类在这个角色上，会使用专门的工具，还是运用自己的专业判断？

能力类型该做吗原因
调用 API、处理 PDF做 · 工具型按需触发
知道自己不知道什么不做 · 元认知应内化为行为准则
用第一性原理思考做 · 认知函数复杂决策时触发
一次性任务不做直接写 prompt 即可
还没跑过 3 次的工作流不做过早固化锁死改进方向
关键发现：self-compass 实验作者把自我能力边界评估从 Skill 删掉、改成 3 行行为准则，效果反而更好——从「需要主动调用的工具」变成了「永远在线的默认思考模式」。有些能力做成 Skill 反而降级了。

越往下越厚，但只有第一层在天天交税——这就是「中心短，辐射厚」的加载版

200+ Skill 时的三个坑

坑 1 · 超过 80 个开始

触发精度断崖式下降

description 语义互相干扰，模型犹豫、误触发。解法：分层可见性，每个 Agent 限制在 40-60 个 Skill 内；大型 Skill 库必须有外部权威分类法当坐标系。

坑 2

同一个 Skill，不同 Agent 行为完全不同

解法：Skill 参数化（parameters 字段），按角色/场景切换行为模式。

坑 3

Skill 之间隐藏依赖会炸

重命名/删除一个 Skill 不触发依赖检查。解法：YAML 前言显式声明 dependencies，Skill-as-Code 纳入 GitOps。

五个设计模式

模式做法适用场景
领域变体references/ 分离变体逻辑一个 Skill 支持多个技术栈
脚本捆绑重复写的脚本固化到 scripts/Claude 每次写类似代码时
模板驱动SKILL.md 定义精确输出模板固定格式的报告、邮件、review
渐进引用大文档放 references/，附目录导航大型参考文档
认知函数定义「如何思考」不是「做什么」第一性原理、批判性思维
最有价值的模式认知函数型 Skill 的价值密度远高于操作型：装一个 PDF 处理 Skill，只在处理 PDF 时有用；装一个第一性原理 Skill，做任何决策时都会更清醒。

跨平台标准与自我进化

agentskills.io — 一份 SKILL.md，30+ 客户端

Anthropic 主导的开放标准：Claude Code、Cursor、Codex、Copilot、Gemini CLI、VS Code 等都能加载同一份 SKILL.md。Skill 不再是某个工具的私产，而是跨平台资产（agentskills.io）。

CQS 评分：让 Skill 自己进化

范式转移（详见关联词条·技能进化）：过去一次写 90 分才上线，现在 60 分上线，靠真实失败迭代。CQS（Character Quality Score）五个维度各 0-10 分——角色一致性、任务完成度、信息准确性、边界意识、表达清晰度。Δ > +0.5 才 promote，否则 discard。关键设计：Shadow 部署（影子 session 不影响生产）+ Capsule 留底（每次改动可回滚）。

对桑老哥的实操指导

  • 不是越多越好：每多装一个 Skill，增加其他 Skill 误触发概率。
  • 装之前问：这个该做 Skill 还是写进行为准则？我真正会用吗？
  • 先 60 分再迭代：不追求一次写完美，收集使用反馈后优化。
  • description 要差异化：语义重叠=误触发，加互斥指向（「Do NOT use for → 其他技能」）。
  • 定期清理：不用的 Skill 白占语义空间，及时删。

前提与局限

  • 本条是规模化之后的工程账：手里没几个 Skill 时，「三层加载」「200+ 坑」只是预防针，别提前优化。
  • 元认知类能力（知道自己不知道什么）做成 Skill 反而变差——先分清能力类型再动手。
  • CQS 评分与 Shadow 部署是作者实践提炼，量化和回滚机制需要 Git 纪律撑着。
