技能进化

稳定 建条 2026-08-03 下次复核 2026-11-18

一句话说清楚

技能不是写完就冻结的静态文件，而是能基于使用数据自我迭代的活物。

PAST

一次性写到 90 分，上线

憋大招：写的时候拼命想全，上线那天就是它的巅峰，之后只掉不涨。

NOW

先写 60 分上线，迭代到 90 分

早上线早收真实失败案例，拿真问题喂它——分数是后来长上去的。

来源：Skill工程实践文章（waytoAGI 飞书）——操作型 Skill 教 Agent 完成一件事，认知型 Skill 改变 Agent 完成所有事的方式。

技能分类：认知型与操作型

类型定义价值例子
认知型改变 Agent 思考方式高密度，影响所有任务PAI、pua、project-status、Telos
操作型完成具体任务按需触发docx、xlsx、lark系列、baoyu系列

进化主要值得花在认知型上——它影响所有任务，每长一分到处受益。

生命周期 8 步法（时间线）

归藏 2026-06：从发现需求到收集反馈，Skill 的一生走这八步，走完再回环。

  1. 1发现真实需求

    从重复工作开始，不先抽象

  2. 2先做高质量产物

    用 Agent 解决真实任务

  3. 3抽象流程

    识别可复用步骤、输入、输出、约束

  4. 4工程化模板

    审美、版式、调用、验证、修复固化

  5. 5跨模型测试

    好模型看上限，差模型保下限

  6. 6封装发布

    GitHub 托管 + README + 示例 + 安装方式

  7. 7内容分发

    小红书 / Twitter / 公众号 / 视频展示结果

  8. 8收集反馈

    只吸收能提升泛化和稳定性的部分——然后回到第 1 步再转一圈

本质：每一次真实任务不只是完成任务，而是在积累下一次能调用的能力资产。（来源：2026-06-12-归藏-万字长文Skills看法，日期类文源不做页面）

价值分布：通用被吸收，专有才值钱

lencx 2026-07：Skill 数量会增长，价值却会分化——先想清楚你的 Skill 站哪一边。

会被模型吃掉的

  • 常见 Git 操作、主流框架脚手架、固定格式转换
  • 通用、公开、能从大量语料学到的技巧
  • 逐渐进模型权重、system prompt 或内建工具，从稀缺资产退化为兼容层

长期值钱的

  • 需要持续更新、组织专属、带真实责任的部分
  • 越深入垂直，价值越来自新鲜性、所有权和真实权限

护城河由这七件东西共同构成：

procedurecurrent sourcestoolspolicyverifierrecoveryprovenance

来源：lencx《Agent 开发指南》（2026-07-28，waytoAGI 飞书）。

迭代闭环

使用中发现问题→ 记录到待优化清单→ 用 skill-creator 优化→ 验证效果→ 更新档案→ 回到使用

闭环不转，Skill 就停在 60 分——进化不是重写，是让这个圈一圈圈转下去。

两条工程教训（进化的规矩）

老金《百万行背后19个坑》（2026-07）

重复错误改规则，别改结果

  • 同一错误在多处反复出现，别挨个补代码/结果，回去改产生这条错误的规则——先损失几份样稿，少报废几百份成品
  • 踩过的坑要「修到上游」：反复出现、能写成预防规则、还能补一条回归测试的教训，才写回长期规则；只在这次任务有用就留本次记录
  • 一次失败被解决 不等于 学会，下一批不再犯才算活下来（呼应 约束先行 长任务四件套的「裁判/断点」）

艾笑 Skill Engineering 1.0（2026-07）

真实问题改根因，不开候选覆盖正式版

  1. Skill 出真实问题（如把原文没说的话写进结果），先判断问题出在哪一层
  2. 开一个「独立候选」改，不覆盖正在用的正式版
  3. 你确认了再应用
  4. 顺手加一个「回归测试」防止下次再犯

与老金是同一思路的工程化落地：在根因层解决，不让补丁越堆越乱。

技能档案去哪了（2026-09-20 迁出）

当前安装清单与迭代日志属环境快照，会过期，不存概念词条——统一维护在 桑老哥私人助理/config/当前全局skill记录.md（与 Skill设计方法论 的实践锚点同款做法）。历史快照（36 个时代）在 git 历史可查。

桑老哥适用

  • 你的 审美规则化、选品直觉这类「独有的、最新的、要对结果负责的」才值得固化成 Skill——它们不会被模型吸收
  • 通用操作（改格式、转文件）迟早变成模型出厂功能，别花精力深做
  • 已上线的 Skill 按迭代闭环转：失败案例是饲料，回归测试是记忆
