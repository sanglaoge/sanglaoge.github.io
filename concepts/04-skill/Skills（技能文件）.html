Skills（技能文件）

稳定 建条 2026-08-03 下次复核 2026-11-18

一句话说清楚

Skill 就是把专家经验、工作流、品味和工具调用，封装成可分发、可复用、可迭代的 Agent 能力单元——本质是给 AI 写的 SOP 手册，但不止是提示词：它打包了流程、模板、脚本、gotchas 和 eval。
归藏定义 · 2026-06

Skill 是「能力商品」，不是「提示词」。提示词容易被复制、没版本管理。Skill 把提示词、规则、示例、工具调用、文件结构、脚本、依赖和使用说明，打包成可安装的能力包。（来源：2026-06-12-归藏-万字长文Skills看法）

技术本质 · 陈菁 2026-07

Skill = API 接口（真干活的机器）+ OpenAPI 描述文档（AI 能读懂的说明书）。大模型只认 description、看不懂代码——说明书和实际不一致，AI 就会被坑死（菜单写红烧肉、端出臭豆腐，AI 真信）。

FindSkill / 描述工程：工具上万不能全塞给 AI（撑爆上下文+变傻），默认只装一个「找工具的元技能」，用时按 description 精准度匹配、临时注入。描述写不清，AI 随机选或幻觉——选 Skill 时先看 description 好不好。

第一站：什么时候该写

一件事最近一周做了 3 次以上、做法基本固定（比如选品分析、写 Listing、周报），才值得做成 Skill。Ian/helloianneo 的五条件判断卡片，五条全中才做：

频率

每天或每周都会做

规则

能写成步骤、清单或判断条件

输入

每次给 AI 的材料差不多

输出

最后想要的结果差不多

风险

做错了可以修改，不会造成严重后果

偶尔才做、输入每次不同、做错代价高的，先用提示词。

第二站：动手前先拆任务

主题压成动作第一刀

Skill 一次只稳定解决一个动作。「内容生产」是主题不是 Skill，「把一段素材加工成 3 条 X 帖」才是。

六维度想清楚再写Ian

  1. 用在哪 — 触发场景和边界
  2. 怎么做 — 步骤和判断点
  3. 给什么出什么 — 输入输出定义
  4. 要用什么 — 工具/模板/参考
  5. 什么算好 — 质量标准+好坏样例
  6. 为什么能行 — 设计依据

你愿点头的标准

核心洞见：提示词越写越长，越容易把「没想清楚」藏起来；终点没定，规则越详细 AI 只会更精确地跑错。具体数据（老板名/客户名/某次格式）只属于眼前这一单活，不能混进长期规则——否则下一个用户来，AI 还端着上一桌的菜单点菜。

三类 Skill，验收重点不同

类型例子验收重点
工具类生图、格式转换输出稳定性
对话类写作、问答输出质量 + 对边界输入的拒绝
审查类校验、评分准确率和漏判

第三站：怎么写好（九条手艺）

  1. description 是分诊台，不是广告语 — Agent 先看 description 再决定读不读正文。写用户会怎么说的话（触发词）、适用边界、不该触发的场景。前半截必须能独立工作，因为 Skill 多了 description 会被截断
  2. 四句话起点法 — 动笔前先写清：替我重复哪件事、用户会怎么说、必须交付什么、什么时候必须停下来。写不明白别动 SKILL.md
  3. 正文四块骨架 — 进入条件 → 工作步骤（每步有产物）→ 质量门槛 → 退出标准
  4. 9 个问题想清楚再写 — 目标/触发/不触发/信息/顺序/输出/完成标准/失败处理/参考文件
  5. 用示例代替解释 — 贴一篇完美输出说「以此为标准」，胜过 100 条规则
  6. 对话转 Skill — 以前的聊天记录是最好的 Skill 原料
  7. 只写 AI 不知道的 — 私有规则、个人习惯，不堆人设。默认 Agent 会读文件、会调工具、会写 Markdown
  8. 脚本 vs 正文分工 — 确定性动作（统计字数、校验 JSON）放脚本，判断和流程放 Markdown；用能力描述代替平台特定工具名，方便跨平台迁移
  9. 黄金法则：用「为什么」代替「必须」 — AI 理解了原因，遇到灰色地带也会做出正确判断。唯一例外：输出格式这类机械要求直接写死（来源：skill-creator 源码）

第四站：怎么测

不要只用最顺的场景测。三类场景必须跑：

标准场景

素材齐全、任务明确——验证主流程

缺口场景

信息不完整——验证 Agent 会不会乱猜

诱惑场景

用户催促或要求跳过验证——验证质量门槛能不能守住

验证观（老金，2026-07）：结构检查脚本两个绿勾，只证明「文件没缺、结构没乱」，证明不了真实任务跑得对。真正要看两个信号：一是证据不够时 AI 会不会主动停下来查（research-needed）；二是第二次撞同一坑，会不会自己绕过去。经验要落到规则/模板/脚本/例子里（writeback）才算「活下来」，光写感人总结没用。最后拍板的还是人。

第五站：五个常见坑（Ian）

  1. 把主题当 Skill — 「内容生产」是主题不是动作，「把素材加工成 3 条 X 帖」才是
  2. 只写流程不写验收 — 没有好坏样例，AI 很难稳定靠近你的标准
  3. 只生成不测试 — 第一次出来最多 60 分，拿真实素材跑 3-5 次再改
  4. 全塞主文件 — 审美标准、案例、检查清单拆到 references/，改起来不牵一发动全身
  5. 过早全自动 — 商业取舍、最终审美选择先保留人工确认点，先跑通半自动
中心短，辐射厚（归藏架构原则） SKILL.md 只放高信号流程和判断；references/ 放重文档按条件读取；scripts/ 放确定性逻辑让 Agent 调用而不是重写；assets/ 放模板、schema、示例。每一句都要问：没有这句，Agent 会不会做错？不会就删。每个 Skill 都是一种税，它在索引后每个会话都在为它的 name 和 description 付上下文成本。
gotchas 比正向原则更有价值：正向原则模型已经知道，负面边界才是专家经验——「不要纯白纯黑」「连续三页相同节奏是 P0 错误」「文字不能压脸」「AI 图只在无合适真实图时使用」，都是从真实失败里总结出来的。Skill 的核心是把人的隐性判断标准固化进去。

第六站：工程化心法与 2.0

Skill Engineering 1.0 五层升级（艾笑，2026-07）

  1. 先判断是否值得做 Skill — 需求更适合脚本/项目规则/插件就别硬做成 Skill（接五条件卡）
  2. 写入前零新增文件 — 先反问：输入是啥、输出存哪、哪些情况不该触发、缺信息怎么办；你确认完整方案后才真正写文件
  3. 改坏就开独立候选 — 正式版正在用，改动先放「候选」不覆盖，确认好再应用
  4. 根因修复 + 回归测试 — 改在产生问题的那一层，不在文件末尾堆「严禁XX」补丁；每修一个失败，沉淀成一个防再犯的场景
  5. 复杂度随风险升级 — 越危险的 Skill，越要设只读边界、停止条件（呼应约束先行的「闸门」）

Skills 2.0 升级

升级作用
内置测试存之前先测效果
A/B 测试新旧版本对比
触发优化自动优化触发词
好 Skill 的价值是让 Agent 少猜——少猜什么时候该用、少猜下一步做什么、少猜什么算完成。

对桑老哥的意义

  • 已经有了共学规则 Skill，这是正确的方向。
  • 日常重复场景都应该做成 Skill：选品模板、文案模板、竞品分析模板。
  • 每次对话发现好的工作流，都可以转成 Skill 固化下来。
