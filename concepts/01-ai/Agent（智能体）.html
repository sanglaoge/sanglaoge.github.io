Agent（智能体）

稳定 建条 2026-08-03 下次复核 2026-11-18

一句话说清楚

下一步做什么，如果是代码提前写死的 → 工作流；如果是模型根据当前情况自己判断 → Agent。

ChatGPT 刚出来只能聊天；现在 AI 能在工作角落里真干活。跨越靠两样：Agent（自主决策的大脑）和 Skill（具体能力的手脚）。

Agent 不是一堆 If-Else 拼接，而是能和环境动态交互的「活」系统。它不再一问一答——你给个目标，它自己想路径、选工具、纠错，直到把事办成。

工作流 vs Agent ·核心

工作流 Workflow
Agent 智能体
路径写死，每一步代码决定
下一步由模型判断
if A → do B; else → do C
想 → 调工具 → 看结果 → 再想
模型不参与决策
关键决策交给模型
核心原则：确定的交给代码，不确定的交给模型。模型负责判断，工程负责兜底。

三大基础

① 模型 · 怎么想

MODEL

不是越强越好。选模型 = 做取舍：能力 × 延迟 × 成本。先保效果再压成本（先跑通再降配）。别让模型做确定性的事——参数校验、格式转换交给代码。

② 工具 · 能做什么

TOOLS

  • 数据类（查/读/搜）：自主调用
  • 行动类（发/改/删）：必须确认

③ 提示词 · 按什么边界

PROMPT

  • 确定规则任务：写清依据、步骤、动作、异常分支
  • 探索型任务：写清目标、工具、约束、停止条件
铁律：行动类工具必须确认——发邮件、删数据、下订单、改合同，凡不可逆、有成本、超授权的操作，都要加一道确认。

六种设计模式（两条线）

第一条线：内部怎么推进

模式特点
ReAct（边想边做）慢但灵活
Plan-Execute（先谋后动）稳但规划易偏
Reflection（做完再检查）质升但贵

第二条线：多个 Agent 怎么分工

模式什么时候用
单体一个扛到底，优先选这个
管理者中心调度，需统一收口时用
交接接力跑，客服分流典型
从单体到多体，增加的是复杂度，不是能力等级。能一个 Agent 完成的，就不要拆成三个。

Agent 五部分

大脑（LLM）+ 工具+ 提示词+ 循环（想→动→看→再想）+ 停止条件

循环怎么收敛归 循环工程 管，安全跑道归 Harness 管——五部分是零件清单，那两条是装配手册。

指挥心法：把「确定交代码」落到日常

原 Agent指挥心法 词条并入（2026-09-18 审计）。核心就一条：确定性写死成规则，不确定性才交给模型判断。

确定 → 交规则
不确定 → 交 AI
SOP、CLAUDE.md、Skill——凡是答案唯一的地方，用规则/代码，不劳烦模型
需要权衡、创造、临场判断的地方，给模型自由度 + 事后验证器兜底
行动规范 5 条（Fable5 Prompt 合集）就是「写死侧」的具体化：把确定的动作写成清单
判完不是散养：验证器接住结果再放行

完整链条：

人定目标→ 规则管确定→ 模型管不确定→ 验证器兜底

与 AI与人的分工原则 一脉：那条管人和 AI 怎么分，这条管 AI 内部怎么分。

桑老哥适用

  • 铁柱就是一个 Agent——你给目标（「查这篇飞书文档」），它自己想路径（lark-cli 抓）、选工具、纠错
  • 铁柱 + 爱马仕双 bot 协作 = 多 Agent 架构雏形（管理者/交接模式的起点）
  • 行动类必须确认这条铁律，就是咱家红黄绿灯的分界依据

前提与局限

  • Agent 能自己跑但不代表不需要人——行动类操作必须确认
  • 单体优先，非必要不拆多 Agent
  • ReAct 循环的停止条件必须硬写（最多 N 轮），否则无限烧 token
