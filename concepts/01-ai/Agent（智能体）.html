Agent（智能体）

稳定 建条 2026-08-03 下次复核 2026-11-11

一句话说清楚

下一步做什么，如果是代码提前写死的 → 工作流；如果是模型根据当前情况自己判断 → Agent。

要给 Agent 下个准确的定义，比想象中难。教科书给的是一串词：感知、规划、记忆、行动——听着都对，可落到工程里，还是不知道第一步该做什么。

所以先别追求完美定义，先看边界：关键不在于它有没有接大模型、有没有调用 API，而在于任务推进过程中那些无法提前写死的关键决策，是不是交给了模型。

来龙去脉：从只会聊天，到能真干活

ChatGPT 刚出来只能聊天；现在 AI 能在工作角落里真干活。这一步跨越靠两样：Agent（自主决策的大脑）和 Skill（具体能力的手脚）。

Agent 不是一堆 If-Else 拼接，而是能和环境动态交互的「活」系统。它不再一问一答——你给个目标，它自己想路径、选工具、纠错，直到把事办成。

工作流 vs Agent ·核心

工作流 Workflow
Agent 智能体
路径写死，每一步代码决定
下一步由模型判断
if A → do B; else → do C
想 → 调工具 → 看结果 → 再想
模型不参与决策
关键决策交给模型
核心原则：确定的交给代码，不确定的交给模型。模型负责判断，工程负责兜底。

三大基础

① 模型 · 怎么想

不是越强越好。选模型 = 做取舍：能力 × 延迟 × 成本。先保效果再压成本（先跑通再降配）。

别让模型做确定性的事——参数校验、格式转换交给代码。

② 工具 · 能做什么

  • 数据类（查/读/搜）：自主调用
  • 行动类（发/改/删）：必须确认

工具本身也要设计，见下「三道护栏」。

③ 提示词 · 按什么边界

确定规则任务：写清依据、步骤、动作、异常分支。

探索型任务：写清目标、工具、约束、停止条件。

两种任务两套写法，见下两例。

工具的三道护栏

工具给得越多，Agent 越容易在接口上翻车。下面三条是反模式对照正确做法：

反模式正确做法
没权限直接返回空 → 模型以为「没填」标「受限」，而不是给一个空值
返回原始 JSON → 模型抓错重点整理成业务状态再返回
工具全平铺 → 模型选错先分流再执行：Router → Executor → Composer
铁律：行动类工具必须确认——发邮件、删数据、下订单、改合同，凡不可逆、有成本、超授权的操作，都要加一道确认。

提示词：两种任务，两种写法

任务类型写清什么例
确定规则任务依据、步骤、动作、异常分支退款处理：每步具体到调哪个 API
探索型任务目标、工具、约束、停止条件旅行规划：不给固定步骤，只给边界

分法就一句：错一步就回不来的活，写到 API 级；怎么走都能到终点的活，只给边界。

六种设计模式（两条线）

第一条线：内部怎么推进

模式特点
ReAct（边想边做）慢但灵活
Plan-Execute（先谋后动）稳但规划易偏
Reflection（做完再检查）质升但贵

第二条线：多个 Agent 怎么分工

模式什么时候用
单体一个扛到底，优先选这个
管理者中心调度，需统一收口时用
交接接力跑，客服分流典型
从单体到多体，增加的是复杂度，不是能力等级。能一个 Agent 完成的，就不要拆成三个。

Agent 五部分

大脑（LLM）+ 工具+ 提示词+ 循环（想→动→看→再想）+ 停止条件

循环怎么收敛归 循环工程 管，安全跑道归 Harness 管——五部分是零件清单，那两条是装配手册。

最小实战：苏州三日行程

不添新概念，只把上面五部分落成一个能跑的最小 Agent：输入一句话目标，它自己查天气、搜景点，最后生成一份三天行程。

「未来三天的苏州旅程」全部输入就这一句，没有附加步骤，也没写死先查什么

三个关键细节

  1. 「未来三天的苏州旅程」——输入只是一句话目标，路径不写死。查哪几天的天气、搜哪几个景点、按什么顺序排，都由它当场决定。这是它和工作流的第一个分岔。
  2. 「天气不是终点，而是约束」——查到某天下雨，就要把露天景点挪走。天气结果不是拿来汇报的，是拿来改方案的。工具结果能不能反哺决策，是 Agent 和「会调接口的脚本」的分界。
  3. 「博物馆周一闭馆，又要回头调整」——排完才发现闭馆，就得回头重排。下一步调什么，取决于上一步查到了什么——这正是 ReAct 适合的场景，先跑起来再修，不要指望一次规划到底。

五部分在这个 Demo 里的具体参数

部分在这里是什么
大脑LLM，负责每一轮的推理
工具查天气 / 搜景点 / 模拟订酒店
提示词告诉它能用哪些工具、按什么规则推进
循环想→动→看→再想，直到行程排好
停止条件最多 12 轮；有成本操作先问人

ReAct 循环的四行格式

Thought: （当前掌握什么、还缺什么、下一步做什么）
Action: 工具名[参数]
Observation: 工具返回结果
Action: Finish[完整的三天行程规划]

前三行是「想—动—看」，第四行才是收工。循环就是前三行反复跑，直到某一次能写出 Finish——写不出，说明还缺东西。

停止条件必须硬写进提示词：最多 12 轮；有成本的操作（订酒店）先问人。不写这一条，它会一直查到「看起来差不多了」才停——而「差不多」并不是你能验收的标准。

指挥心法：把「确定交代码」落到日常

原 Agent指挥心法 词条并入（2026-09-18 审计）。核心就一条：确定性写死成规则，不确定性才交给模型判断。

确定 → 交规则
不确定 → 交 AI
SOP、CLAUDE.md、Skill——凡是答案唯一的地方，用规则/代码，不劳烦模型
需要权衡、创造、临场判断的地方，给模型自由度 + 事后验证器兜底
行动规范 5 条（Fable5 Prompt 合集）就是「写死侧」的具体化：把确定的动作写成清单
判完不是散养：验证器接住结果再放行

完整链条：

人定目标→ 规则管确定→ 模型管不确定→ 验证器兜底

与 AI与人的分工原则 一脉：那条管人和 AI 怎么分，这条管 AI 内部怎么分。

桑老哥适用

  • 铁柱就是一个 Agent——你给目标（「查这篇飞书文档」），它自己想路径（lark-cli 抓）、选工具、纠错。
  • 铁柱 + 爱马仕双 bot 协作 = 多 Agent 架构雏形（管理者/交接模式的起点）。
  • 行动类必须确认这条铁律，就是咱家红黄绿灯的分界依据。
  • 概念馆批量建页那种活，就是「一句话目标 + 硬边界 + 硬停止条件」的最小实战——规范是边界，页数是停止条件。

前提与局限

  • Agent 能自己跑，不代表不需要人——行动类操作必须确认。
  • 单体优先，非必要不拆多 Agent。
  • ReAct 循环的停止条件必须硬写（最多 N 轮），否则无限烧 token。

收尾自检四问

Agent 跑不稳时，按顺序问一遍，往往比换架构有用：

  1. 目标有没有说清楚？
  2. 工具边界有没有设计好？
  3. 哪些地方该让模型判断，哪些地方该交给代码？
  4. 有代价的动作，有没有让人确认？
