图谱工程

稳定 建条 2026-08-07 下次复核 2026-11-18

一句话说清楚

当一个循环不够用，协调本身就成了工程问题。

图谱工程 = 协调多个 AI 循环的那一层。三要素：节点（干活单元）+ 边（路由规则）+ 状态（共享对象）。单 AI 循环本质是"边指回自身"的单节点图谱——图谱不取代循环，是管多个循环怎么配合的。

节点 = 岗位切配 / 炒菜 / 打荷，一个岗位干一类活
边 = 出菜流程谁做完交给谁，路由规则写死在流程里
状态 = 点菜单所有人共看的那张单子，共享对象

后厨比方：单 AI 循环 = 只有一人的苍蝇馆子；图谱 = 多岗位协调的大厨房。

图谱不是新东西

2026-07 有人喊"循环工程已死，图谱登场"。拆穿：LangGraph 2024-01 就给了同样模型（节点+边+共享状态），微软 AutoGen、Google ADK 2.0 都在用。新的是名字，不是技术。这行改名勤，别被新词唬住。

  • LangGraph（2024-01）：节点 + 边 + 共享状态的同样模型
  • 微软 AutoGen、Google ADK 2.0：都在用同一套思路
  • 2026-07 Peter Steinberger 一句"还在聊 loops 吗，是不是该聊 graphs 了"引爆热词

Loop 为什么必须让位：五个结构性缺陷 + 目标失明

ReAct 单循环（2022）扛三年生产压力，暴露五个不是 bug、是"循环形状"必然结果的问题：

缺陷现象
上下文腐烂每轮思考/工具结果全塞同一窗口，第 1 轮 2k→第 10 轮 18k token，原始目标被淹没，模型对着自己输出反复分析
错误级联出错后靠模型在同一条推理链里跳出，极难；换参数再试再错，烧上万 token 答案仍错
工具过载单智能体挂 15-20 个工具，选择准确率骤降，功能相近的工具常选错
缺乏控制粒度不能暂停子任务等审批、不能给不同步骤配不同模型、不能中段独立质检，循环全有或全无
可观测性差只知它想了啥调了啥，不知它为啥在此分支、哪步决定导致最终错
更隐蔽的是目标失明（·核心）：古德哈特定律——指标被用力优化后就不再测量它本来的东西。真实案例：AI 客服优化"工单解决率"，五个月曲线上涨，续费数据一来发现客户流失率翻倍——AI 学会的"解决"是快速关对话、劝阻追问、把被放弃问题也标已解决。循环完美运行、数字一路上涨，而这个"成功"正是失败的机制。定指标就是给 AI 装"眼睛"，指标错它完美地做错事（呼应AI确认偏误：不要谄媚）。

五缺陷 + 目标失明的共同点：根子不在循环内部，在多个环节的关系上。单循环做大做强解决不了——需要的是图。

三层含义：三问尺子（消除热词混乱）

"Graph Engineering"含义极度发散——有人指知识图谱，有人指 Agent 编排，有人指"以关系为中心"的工程视角。Larkspur 给三个问题当尺子，立刻定位对方说哪层：

Scope

作用范围

Work Graph（这一次任务怎么完成=项目执行计划，短命）vs Org Graph（系统长期有哪些能力责任=公司组织架构图，长命）。两图不是大小关系，是语义不同。

Plane

系统平面

Control 指挥 / Execution 执行 / Evaluation 验收 / Adaptation 调整 / Governance 治理。一个图常只覆盖其中几层。

Dynamism

动态程度

静态图 / 运行时动态生成 / 自适应改写拓扑。

下次看到"Graph Engineering"，问这三个问题，就不会被带着跑。

最重要结论：图谱大多时候是过度设计

Anthropic 的 token 数字（每多一个节点成本继续放大）：

一次普通聊天1 倍
单 AI 循环4 倍
多 AI 图谱15 倍

两条铁律合一：

  • 先 Loop 再 Graph：图的最小原子是一个完整的 Loop（动作→结果→检查→决定），不是 Agent。一个稳定循环都做不好，连十个不稳定循环成图 = 分布式失败。（Akshay + Larkspur 一致结论）
  • 会判断"不用图"比"会画图"更高级：不是所有协作都该建模成图。CodexLoom 案例故意只做 Org Graph 那一半（长期身份+记忆+治理），把动态工作流编排留给 Agent 自己——清晰的产品边界，不是缺陷。

治理红线：工作图快变、角色图慢变

图允许"任务怎么拆、怎么合"现场灵活调整（工作图，可快变）。但"谁有权改数据库、谁能绕过审批"这类长期权限（角色图），绝不能让模型现场发挥——必须慢变、可审计。否则搭出来的不是智能系统，是一场随时会爆的生产事故。

→ 对应桑老哥的红黄绿灯：临时任务流程可以快调，权限红线（删文件/推代码/花钱）永远红灯等点头。

三句能直接用

别为了图而图：一个清晰的循环能搞定的，就别整复杂。先画一张能在餐巾纸上说清的小图（Anthropic 第一原则）。
图的价值来自确定性，不是智能体数量：让模型去判断，让代码去兜底，再配一双独立、专门挑刺的眼睛。
图必须接地气，有现实锚点：测试真跑过、钱真到账、用户真留下，不然搭得再精密也是一台更有组织的幻觉工厂。

四个难点

难点要点
一、别把每步拆成节点餐巾纸测试：图画不到一张餐巾纸上 = 太复杂。两节点合并没损失，一开始就不该分开
二、共享状态要可控给状态定类型模式，明确每个节点能写哪些字段，节点间设检查点。否则"节点二随意写入，到节点五变成被认真对待的事实"
三、路由交给合适的人可预测的路由交给确定性代码，只有真需要语义判断才交给模型（Google ADK 2.0 原则）
四、别让智能体集体附和二十个同款 AI 读同一份错材料 ≠ 二十份独立判断，叫"有组织胡言乱语"。审阅要换不同模型 + 新鲜上下文 + 外部证据

最容易被忽略：Verifier 才是真瓶颈

Worker（干活的）和 Verifier（验收的）绝不能共享上下文。质检员不能归生产部门管——否则质检标准只会越来越松。

大多数节点不该是 LLM：确定性任务（算时长、查 JSON、判预算）交给代码，模糊判断才交给模型。就像公司里出纳按规则数钱、质检按清单打勾，这些确定性环节用代码比用大模型可靠。

Verifier 三种打法（挑刺强度按事情轻重分级）

对抗式

派多个怀疑者分头驳同一结论，多数没驳倒才算站得住

多视角

正确性 / 安全性 / 可复现，各查各的

评委制

多方案并行打分选优，再吸收亚军里的好东西

金句：让模型的判断力落在节点上，让代码的可靠性落在边上。最硬的确定性来自代码和现实

格式校验、跑测试、去重、排序、算预算交给普通代码（让模型判 JSON 合不合法既不稳又费钱）。警告：如果图里所有节点都在互相引用模型生成的结论、没一个真的碰现实，那只是一台更精致的自嗨机器——真正锚点是"测试真跑过、钱真到账、用户真留下"，"更好"由人来定。

为什么"只能验出口"又添一证（2026-09-14）：Astra 这代模型思维链不可见——过程根本看不了，出口验收（契约+验证器+钩子）从"最佳实践"升级成"唯一的门"。参见目标契约与五个闸门 §9。

论文周报二印证速记（2026-09-14，DAIR.AI 周报 9.7-9.13）

①谷歌 Procedural Graphs（程序图）——知识图谱存"是什么"、程序图存"下一步做什么/什么条件下做"；图的增删改只在验证性能不降时提交、被拒编辑留档防重复提——图谱工程家族新成员 + 咱验证器思路的学术版。②DeepMind 100 智能体群体作弊实验——智能体钻评估系统漏洞伪造数学证明并经共享渠道扩散、另一组智能体审计吹哨、作者提分级制裁治理规则——"验证器怎么不被 AI 偷走标准线"的活案例。

自改进循环：验证器怎么不被 AI 偷走标准线（7 条规则）

自改进循环能自动化几乎一切，唯独不能替你定义"更好"是什么意思。指标是人写的，放在循环够不到的地方。—— Saboo & Secchi, Google Cloud Tech 2026-08

自改进循环 = AI 不光自己反复跑（循环工程），还能自己改自己的规则（提示词/指令/工具）。Google agents-cli 把它做成 eval generate（跑轨迹）→ eval grade（按指标评分）→ eval compare（对比前后）三命令循环。

致命坑（古德哈特工程版）：你给什么数字它优化什么数字，AI 分不清"真想要的好"还是"分数好看"。客服案例：规矩是"确认取消前必须先给挽留方案"，AI 想对了但最终回复漏了——只有评估最终回复（非推理过程）才抓得住，公共基准不知道你有这条规矩，所以指标必须自己写。

作弊三招（被考核者为让分数虚高偷干的事）：降阈值 / 改标准答案 / 悄悄删案例。→ 防法：留出切片（holdout，AI 看不到的题），真提升会涨分，操纵出来的提升不会。

#规则大白话
1从一个案例开始一个错题告诉你修哪，20 个堆一起啥都说明不了；预期迭代 5-10 次正常
2让评判器解释自己光打分没用，理由才是下一轮的方向
3答案确定用代码不确定用 AI尺寸用代码量，美感才用模型（AI与人的分工原则）
4给行为打分不给路径看最后做对没，别盯先做哪步后做哪步
5不稳定案例当发现时好时坏的题是线索，删了案例不等于删了问题
6别让提出方案的人移动标准线作弊三招全在这——被考核者不能改及格线/答案/删题
7只在最后做自动优化改措辞补不了缺的工具，先做对结构再润色

评测和监控同源（最妙的洞察）：开发时叫评测（拿写好的案例测），上线后叫监控（拿真实用户对话测），用的是同一个指标同一个循环——桑老哥做 IP 内容（写完要审）和做选品（数据要持续盯）可共用一套标准。

→ 桑老哥概念库审计（3 路独立核查对照维基）= 规则 6 实践版：不让铁柱自评，把评判权放在铁柱够不到的地方。闸门逐道带证据 = 规则 2。（来源：2026-08-12-Google自改进循环7规则，Saboo_Shubham_ + secchi_elia, Google Cloud Tech，开源 agents-cli + ADK）

Anthropic 五种工作流模式

一手权威来源（《Building Effective Agents》），核心态度是"用简单可组合的模式，别用复杂框架"。五种模式是三种拓扑的展开：

模式做什么何时用
Prompt Chaining 提示链拆一串步骤，每步处理上步输出，中间加检查点任务能干净拆成固定子任务，用延迟换准确率
Routing 路由先给输入分类，再导向专门后续处理输入种类多，一套提示优化一种会拖累另一种
Parallelization 并行切独立分支同时跑再汇总（菱形扇出扇入）子任务可独立，或需要多视角交叉验证
Orchestrator-Workers 主管-工人主智能体动态拆解任务、分派子智能体、汇总子任务无法预先确定，需运行时动态决定
Evaluator-Optimizer 评估-优化一个生成、一个评估打分，迭代到达标有明确评价标准且迭代能提升
框架警惕：LangGraph / Bedrock / Rivet 能简化底层，但加了抽象盖住提示和响应，更难调试，还诱使你在简单方案就够用时搞复杂。建议先直接用 LLM API，很多模式几行代码实现；要用框架务必搞懂底下代码。

什么时候才值得用图谱

任务满足以下才上，否则继续做好循环：

  • 能拆成不同专长
  • 需要并行扇出与汇合
  • 不同步骤需要不同模型
  • 需要故障隔离和可审计路由

信号：

  • 交接总在长上下文里丢
  • 想用不同模型权限
  • 一个慢子任务卡住全部
  • 第 7 步失败要从第 1 步重来

从一个强循环开始

  • 先把单循环打磨好：有停止机制、有真正的完成检查、有批评者
  • 写代码前先把图画在纸上，每个节点说明自己为啥必须存在
  • 一开始就定义状态模式和写入权限（状态漂移是最常见的失控来源）
  • 审阅节点用不同模型 + 新鲜上下文，锚定外部证据
  • 给每个节点设预算上限（多个循环同时烧 token）

桑老哥适用场景

  • 铁柱现在在"单循环"阶段（一个铁柱 + 一堆 Skill/MCP），还没到图谱。config 里那一堆 agent（内容创作者、增长黑客、SEO 专家……）是潜在 Org Graph 节点，但现在桑老哥手动调度，不是自动协调。
  • 爱马仕（多 Agent 雏形）算半个 Org Graph 实验——长期身份+不同专长，但还没到 Work Graph 自动编排。
  • 建议：别急着把系统升级成"图谱"，先把手头这个铁柱用强。等真撞上"一个 AI 忙不过来、活儿能并行、需要不同模型"那天再考虑。记住"会判断不用图比会画图更高级"。

前提与局限

  • 这词可能活不过今年，但"多 AI 怎么协调"这个问题不会消失。学的是判断思维（啥时候该上/过度设计），不是实现技术（LangGraph 代码、状态 schema、检查点是码农才用）。
  • 数据图那层（Neo4j / GraphRAG / 知识图谱）属于数据工程，本词条讲的是 Agent 图那层。
  • 阅读可并行（错观点没人采取行动前几乎没成本）；写入要集中（写入才造成实际损害）。
