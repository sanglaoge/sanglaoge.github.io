验证阶梯

稳定 建条 2026-10-29 下次复核 2027-01-29

一句话说清楚

别指望某一层检查挡住所有问题——设计成「多层各抓一类 + 承认每层都会漏 + 最后一层是能快速撤回」，并且给审查设轮次上限。

一句话记住：审查的上限不是「零缺陷」，是「缺陷的可撤销性」。

来龙去脉

2026-10-26，Addy Osmani 在 X 上转述 Anthropic Claude Code 团队的代码审查流程。背景数字很硬：

90%的 Claude Code 代码由 Claude 自己写
2,500 → 30,000+单体仓库每天合并的变更（5 月→9 月）
翻一倍多Claude Code 自己的 PR 数量（6 月→9 月）

在这个速度下，逐行人工审查不是「变难」，是不可能。他们的解法不是少写点，也不是不审查，是把审查本身重构成一套分层系统。

为什么值得单独成条：这是 2026-10-28 白皮书「门槛从能生成变成能验证」的具体实现版——白皮书说「要验证」，这篇说「怎么验证、几层、谁验、验不过怎么办」。

核心一：先把那个错问题换掉

错的问法（过程指标）「是否有人读了代码？」——只问有没有人看过，问完也说不清这次改动到底危不危险。
对的问法（结果指标）「这个变更可能出什么问题，哪种检查才能发现它？」——问完就能决定派哪一层上。

副产品：审查的时机也变了。传统是「写完、提 PR、等人看」（事后检查），他们改成「写的过程中不断查」——原文比喻：更像写作时不断进行的拼写检查。

核心二：七层，没有一层是「终审」

  1. 1PR 前验证：跑测试、跑构建、截图与设计稿比对；再用全新上下文的子 agent 审 diff。谁干：AI 自己
  2. 2每个 PR 都过 AI 审查：多个 agent 并行找 bug → 投票判有效/误报 → 过滤纯风格问题 → 按严重度排序。谁干：AI
  3. 3安全审查：有未解决发现就堵住不让合并。谁干：AI
  4. 4CI 硬检查：lint、类型检查、全平台测试、构建（典型 CLI PR 跑几十项）。谁干：自动
  5. 5按风险分级的人工审批：低 0 人 / 中 1 人 / 高 2 人。谁干：人
  6. 6合并队列 + 功能开关 + 分级灰度：内部员工先吃到。谁干：自动
  7. 7快速回滚：开关一关、版本一回退，几分钟撤销大多数错误。谁干：人 · 这一层不是更严，是更快
每一层都会捕获一些 Bug，同时也会遗漏一些。很少有 Bug 能穿过所有层级；如果有漏网的，我们有回滚机制。

设计假设从一开始就是「一定会有漏网的」——所以最后一层不是「更严的审查」，是「更快地撤回来」。

核心三：人的时间要算两笔账

我们不仅算人们花在代码审查上的时间，还要算花在修复由不良代码引入的 Bug 上的时间。如果只减前者不减后者，我们并没有真正节省人的时间。

所以他们用护栏指标，不用单一目标：

  • 追的：每个 PR 的中位人工批准数（含 P95）、人工评论数、PR 等人工的时间
  • 卡死的：回滚率、事故率——这两个一涨，说明你不是省了时间，是把时间挪到后面去了

核心四：风险由「变更」决定，不由「谁写的」决定

风险例子人工审批
低文档、文案、内部功能、带功能开关的增量改动0 人（自动化全过就放行）
中普通产品改动；缓存 / 自动更新器 / 系统提示词这类敏感区1 人
高最高风险代码、CI 工作流文件、所有者标记为敏感的路径2 人

三条硬规矩：

  1. 一个分类器判风险等级，另一个分类器判「这个变更是否确实需要额外审批」——风险等级本身不等于必须再批一次。
  2. 智能体的批准不算人工批准。「AI 说没问题」永远不能顶替「人看过」。
  3. 审批只对一个提交有效。有新提交（agent 又推了东西、有人手解了冲突）→ 全部审批作废，重新批。

核心五：审查会无限循环，必须强制收敛

这是全文最诚实、也最反直觉的一段，讲他们自己搞砸的地方。

现象：CLI 项目里有一个 PR，因为「AI 作者 + AI 审查者」来回，一夜之间循环了五十多轮，最后是人工掐停的。

根因：对反复被标记的问题跑 git blame，约 59% 的代码在第一次提交时就已经存在——审查很少发现新 bug，每一轮都在翻出更老的 bug。他们原话：「我们把情况变得更糟了，因为我们养成了默认多跑几轮的习惯。」

四招收敛

  • 三轮之后强制要求作者重新评估方法（不是继续改）
  • 初始轮之后的重新审查只审新 diff
  • 明确 bug 类别，一次修一整类，不是修一行
  • 不重复报告已经报过的问题
指标收敛前收敛后
平均审查轮次2.081.32
需要 5 轮以上8.9%1.5%
一轮就过65%78%

错法 → 对法

错法对法
「谁读了代码？」（过程）「这个变更可能出什么问题，哪一层能抓住它？」（结果）
指望最后一层把关，前面随便前面几层先清常规问题，人的注意力只留给高风险和判断类
追求「零缺陷」承认会有漏网，把力气花在「能几分钟撤回」
只砍审查时间，不管修 bug 时间两个一起算，用回滚率/事故率当护栏
所有改动一视同仁，全都要人盯按变更风险分级，低风险自动放行
AI 审过就算过智能体批准 ≠ 人工批准；新提交要重新批
「多跑几轮更保险」三轮不过就怀疑方法，之后只审新 diff
每轮都从头审全篇初始轮之后只审增量

边界（什么时候别用）

  • 有明确对错的任务才适用。代码 diff 有「对/错」，审美判断没有。「三轮上限」搬去做审美验收要打折——审美上三轮反复可能是正常的。
  • 小项目是杀鸡用牛刀。单人、无外部用户、改坏了顶多重做——七层全套是浪费。原文也说了，这套流程是被「每天三万次合并」逼出来的。
  • 「最后一层是回滚」有前提。版本可回退、开关能关、旧产物还在。没有这个前提，最后一层是空的——那你其实只剩「更严的审查」，风险全压在人身上。
  • 护栏指标不能只用一个。只看「审查轮次降了」会逼人放水；必须同时盯回滚率和事故率。

桑老哥适用

对照下来，你的视频工厂已经有这套东西的雏形，缺三块：

你已经有的对应哪一层
门槛项客观实测（规格/时长/LUFS/静止帧/词数/停留/禁词/溯源）第 4 层 CI 硬检查
观感 6 项人工打分（铁柱初评、桑老哥终评）第 5 层人工审批
验收错题本 + 必停点第 1 层「给自己一份可运行的检查清单」
「验收一律正向实测，静态量测/缩图目验不作数」与原文「别说任务完成，给我看结果」同一条
三款成片留旧版文件第 7 层的原料（但没写成规矩）
缺的三块：①没有「回滚」这一层——验收是过/不过二元，没有「改坏了能几分钟回到上一版」的显式规矩；②没有分级——「改错别字」和「改渲染逻辑」用同一套验收，这是累的根源；③没有收敛规则——该立的规矩：改三轮还没过，不是继续改，是回头怀疑方法。
