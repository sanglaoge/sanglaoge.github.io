目标契约与五个闸门

稳定 建条 2026-08-03 下次复核 2026-11-18

核心洞见

AI 现在最吓人的地方，不是它懒，是它太勤快。方向一旦歪，它会非常认真地把错误做完整。—— 老金（金先森）

这是什么：GoalPro 与目标契约

GoalPro 是一个 Skill（github.com/KimYx0207/GoalPro），给 Codex 和 Claude Code 共用。它的任务不是替你干活，而是执行前把目标写清楚。

输入一句模糊请求，输出一份 Goal Contract（目标契约），然后停住等你确认——默认不执行。

Goal 三要素（Codex /goal，lencx 2026-07）

outcome

要什么结果

不止说"做什么"，说清达成什么才算数

constraints

不能碰什么

边界、禁区、必须问人的风险

verification

怎么算完成

由外部证据说话，不由模型自述

完成与否不能由模型自述，要由测试、可测指标、diff、截图、外部状态或人工验收确认。目标可暂停、恢复、编辑，但不会因此获得更宽的 sandbox 或审批权限。

没有停止条件和预算上限的 Goal，本质是无限循环。（来源：lencx《Agent 开发指南》2026-07-28，waytoAGI 飞书）

五个闸门（逐级抬升的台阶）

1

意图

翻出真实不满，不复述原话

"优化项目"背后到底是嫌可维护性差、交付不可信、还是上一个 AI 跑偏了？要挖出来。

2

边界

做 / 不做 / 必须问人的风险

没边界，AI 会把自己的"合理扩展"当成你的需求。

3

证据

防"假完成"

命令通过 ≠ 结构检查 ≠ 本地验证 ≠ 线上验证 ≠ 人工验收——很多失控就是把其中一个当成全部。

老金最看重
4

暂停

写进目标的硬规则

删数据 / 碰密钥 / 改公共接口 / 发布上线 / 路线互斥 / 无法验证 → 必须停。不是软建议。

老金最看重
5

验收

交出证明目标达成的材料

测试、截图、diff、行为变化、剩余风险，要对回最初的目标。

台阶越走越高：从挖清意图，到交出证据——③④两道是防"太勤快做完整错"的关键闸。

prompt-only 闸门（设计灵魂）

Skill mention ≠ 执行授权。你说"goalpro"，它写目标；你说"按这个目标执行"，它才动手。

老金的设计哲学：

  • 目标生成阶段最怕越权
  • 执行阶段最怕没目标
  • 两件事混在一起，体验上省一步，但边界会变糊
很多失控不是从大错误开始的，而是从一句顺手的"我来继续"开始的。

适用与不适用

场景用不用
改错别字、查文件名、补一句文案别用，太重
跨文件、跨模块、影响发布、需要研究判断用，先写 Goal Contract
自己都觉得容易跑偏的任务用，先写

与奖励工程的分工（2026-08-16 桑老哥讨论定）

Goal 三要素（outcome/constraints/verification）与奖励工程RewardEngineering三步法（定目标/设负向约束/定验收）同源同一套，不重复讲内容。

分工一句话：奖励工程管「规则写得对不对」（内容论），目标契约管「放不放行」（流程风控论）。本条的增量全在：① 先确认再执行（prompt-only，对菜单再下单）② 防假完成（证据五级不混）③ 暂停门六必停 + 最终验收人 + 两套模板（五要素填空/长任务卡）。

五要素填空：日常小任务模板

长任务用长任务卡，日常给 AI（铁柱/lark-cli/任何 Agent）下任务用五要素填空——本质是 Goal 三要素拆成的 5 个填空题。来源：AJ《100 个飞书 CLI 真实案例》@ 飞书 AI 绝活大会。

要素问自己例子
范围哪个时间段/哪个群/哪个项目？"上周的课程群"
目标要解决什么问题？"把高频问题沉淀成 Q&A"
处理去重/分类/分级/脱敏？"合并重复问法、补答、清敏感信息"
交付写成文档/表格/回复群？"写成飞书文档"
校验完成后查什么？"核对每条回答出处"

随手派活：「帮我整理下这个课程群」→ AI 一头雾水，不知道边界

五要素版：「范围 上周课程群 / 目标 沉淀高频问题为 Q&A / 处理 合并重复、补答、清敏感 / 交付 飞书文档 / 校验 核对出处」→ AI 知道干啥、干到啥程度、交到哪、怎么算对

配套五步循环（飞书 CLI 实战）：

找（定位时间/人/项目）→ 读（理解原文上下文）→ 理（去重/分类/分级）→ 写（写回文档/Base/群）→ 验（重新读取确认）

简单任务前两步够，任务越重要越要走到"验"——校验产生信任，成本最低的信任。验的内容：记录数 / 权限 / 链接。

长任务卡模板（老金《百万行背后 19 个坑》2026-07）

大任务放手跑前，先填这张卡（与五个闸门一一对应）：

长任务卡字段对应闸门说明
目标 / 完成标准①意图 ③证据 ⑤验收看到什么证据才算结束；填不出先别扩 Agent
规则书（固定做法/必须停问的情况）②边界哪些照做、哪些重做
裁判（测试/对比/样例/人工）③证据用坏样本测过才可信；能运行 ≠ 行为一致
任务账本（自动变下一张待办）③证据别只存聊天里
断点（中断后靠哪个文件继续）③证据换人看文件能续上才算合格
停止条件④暂停出现什么情况立刻暂停不耗资源
最终验收人⑤验收谁为点通过负责（AI 扛不起责任）
填不出完成标准先别扩 Agent；裁判没拿坏样本测过先别信；账本只在聊天里先别跑一夜；断点说不清先把任务缩到一次会话能收住。—— 老金原话

运行时自纠错循环（CyrilXBT 2026-07）

长任务卡管的是"动手前"，这一节管的是"跑起来后怎么自己抓错、别让你当人肉校对"。三个角色必须分开（核心是隔离盲点）：

构建者

产出第一次结果，给最大创造空间，不要求一次完美

评审者

不产出，只按书面标准挑错；关键是它得有构建者没有的真实依据（原始要求/源文档/测试/数据），否则只能看"通不通顺"，一份自信地错、格式优雅的答案每次都能混过去

管理者

读评审判定，决定交回重写 / 升级给你 / 标记完成；停止条件在这

结构化交接（比提示词重要）：构建者输出"交付物 + 置信度 + 已知不确定项 + 所做假设"；评审者回"通过/失败/需修订 + 核查依据 + 具体问题描述 + 置信度"。松散文字会漂移，第 100 次也得稳。

停止条件必须写死在逻辑里（不是软提示词）：

  1. 最大迭代次数（如 3 次还失败就停，交回给你）
  2. 可机械验证的阈值（"5 项要求全打勾"，不是"差不多"）
  3. 成本/时间上限（超了立刻停，不管完没完）
同上下文自查没用：让模型在同一段对话里"检查你刚写的"会护短——用产生错误的同一套思路审自己，越看越对。必须换调用、换提示词、换参照框架，让评判不被同一组盲点污染。这就是循环工程独立验证器的来由。
与五个闸门的关系：闸门①②③④⑤是"动手前定规矩"，自纠错循环是"动手后保质量"。评审者=证据闸门（③）的运行时版，管理者+硬停止条件=暂停闸门（④）的运行时版。两者合起来：任务前先写契约，任务中自己纠错，出了真问题才交回人。

Astra 配置翻转印证（2026-09-14，AdiiX X 帖）

模型换代，约束跟着翻转——"为旧模型装的每个刹车，都是给本来就会刹车的车又装刹车"：

  • 完成契约必须可脚本检查：DONE 的定义 = "文件存在/测试通过"这类能跑命令验证的，不是"觉得做完了"——正是停止条件"可机械验证的阈值"的同源印证
  • 授权台账（新增概念）：哪些动作能自动做、哪些必须点头，写成清单——别让它猜。咱家红黄绿灯分级就是台账的民间版
  • 删刹车三例：读全部文档→给地图；"有风险先问"→列具体类别清单；做完停下等确认→审批放最后一步。感觉词全换类别清单
