Agent组队机制

稳定 建条 2026-09-01 下次复核 2026-12-01

一句话说清楚

现在的 AI 组队是「包工头派活」——Leader 当分发器、成员互相隔离。该学真团队：懂业务能兜底、好好说话、先商量再开工、成员互相通气。反过来的官方共识（2026-10 补）：默认单干，拿不出理由别组队。

砍掉协作机制，20 个 Agent 干活 = 1 个 Agent

多 Agent 的价值 100% 来自协作机制本身，堆数量不产生任何价值

现状：Leader-Worker 架构的毛病

主流框架（CrewAI / AutoGen / MetaGPT）的 Leader 本质是调度器：切任务→扔给 Worker→收结果。对比真团队有四大缺陷：

无方案讨论

直接拆活，不商量怎么干

Worker 互相隔离

只跟 Leader 单线联系，互相不通气

无进度管理

干到哪了没人跟踪

改方案不审查

出错才返工

阿里 AgentTeams 开源案例证明：基础设施已成熟（通信、共享存储、安全都解决了），缺的是协作语义——「能不能说话」解决了，「该说什么、怎么共识、说完怎么沉淀」没解决。

五问五答：五篇论文串成生命周期链

问题代表工作答了一半的
队形怎么排协作类型学 (arXiv 2501.06322)五种形态（Flat/Hierarchical/Team/Society/Hybrid）无银弹；需互相救场的活 Flat 反而优于层级
活怎么分MetaGPT / Agent-Oriented Planning写死流程求稳 vs 动态拆解求准；但都是自上而下，Worker 不参与定目标
目标怎么对齐OKR-Agent (arXiv 2311.16542)OKR 搬给 AI 可行；但 Worker 只能领任务，不能说「这活我干不了」
经验怎么攒Experiential Co-Learning (ACL 2024)个体长记性（0.43 → 0.73）；攒的是「我手艺更好」不是「我们配合更好」，未成团队资产
团队怎么进化Meta-Team / EvoChamber三层演化（个体/交互/团队）+ 6.6%；刺眼数字：去掉协作机制，20 Agent = 1 Agent

作者方案：好领导四条 + 三步开工 ·核心

1深度参与方案制定

不是黑盒切分，Leader 懂业务

2先商量共识再执行

与 Worker 讨论后再动工

3能兜底

Leader 用更强模型 + 更长 context，不是弱化版 Worker

4审查方案变更

防局部最优毁全局

人类的开会成本（沟通/等待/情绪）在 Agent 侧几乎为零，三步秒级完成

最值钱发现：启发式管理（对 AI 好好说话） ·核心

同一个 AI、同一个任务，两种派活姿势，产出两副面孔：

命令式

「你负责 X，别搞砸了。」

产出保守机械，只做最低要求。

鼓励式

「这块我看好你，放开试几种思路。」

深度和创造性肉眼可见提升。

机理：主流模型经 RLHF 对齐——「鼓励探索」语境挂着高质量回复分布，「命令否定」语境挂着保守免责分布。给 Agent 什么语气，就激活什么行为模式。

派活姿势两条

  • 不说「你去做 X」，说「这个方向你的视角比我细，先说你会怎么切入」
  • 验收不只挑毛病，明确指出好在哪里——为下次高水平输出立锚点
冷冰冰的派发 = 永远只用到 AI 的 60% 能力。

组不组队：两家官方怎么说 ·核心

这一节补的是反面：上面讲的都是「怎么组好」，而两家官方文档给的第一句都是先别组。

LangChain · 2026-01-15

从单智能体开始，先加工具，再加智能体。

Anthropic · 2026-10-22

带技能的单智能体，质量往往优于子智能体设计，成本和延迟通常更低。

四条判据：拿不出任何一条，就别开子智能体

  1. 单循环因上下文膨胀，出现可衡量的性能下降
  2. 多个任务需要在全新窗口并行，干完即弃
  3. 单个智能体选不准工具
  4. 系统提示词里有互相冲突的指令

选型表：四种需求换四种架构

你的需求该用哪种关键代价
多个不同领域（日历 / 邮件 / CRM），要并行执行子智能体（主管集中编排）结果要多绕一道回主管，每轮多一次模型调用
一个智能体多种专业，轻量组合技能上下文累积，多领域时 token 最贵
带状态转换的顺序流程，全程与用户对话交接必须顺序执行，无法并行
不同垂直领域，并行查多源再综合路由器无状态，每次重复付路由开销

注意这张表读法：技能是默认档，子智能体只在「多领域 + 要并行 + 结果可汇总」时赢；否则多花的每一次调用都是纯成本。

组队的账：三个数字与四个坑

两家都给实测数字，账不是按「谁更强」算，是按场景算：

场景单智能体路线子智能体
一次性请求技能 / 交接 / 路由器各 3 次模型调用4 次
同一请求第二轮技能与交接降到 2 次（省 40%）恒定 4 次
多领域查询（比较三种语言）技能 3 次 / 15K token5 次 / 9K token（少 67%）

最狠的一条来自企业客户对比：拿自家多智能体框架跟单智能体循环比，后者快约 2 倍。也就是说，组队只在「本来就必须并行」的活上划算。

四个失败模式：组织问题投影成架构

上下文交接有损

每传一次手，信息掉一层

子智能体泛滥

每团队一个，几百个重叠、无主

弗兰肯提示词

各团队各加一句，规则互相打架

评估被稀释

各自过拟合自己那一格，整体没人看

Anthropic 的原话意思：架构成了组织架构图的翻版——康威定律。你公司怎么分组，你的 Agent 就怎么分裂。

三条操作细节（都是踩过坑换来的）

  1. 按上下文划分，不按问题类型划分——按问题分就变成传话游戏，每交接一次失真一次；好的切法是独立研究路径 / 接口清晰的组件 / 黑盒验证
  2. 折叠要一次一个，用端到端评估对比——他们踩过：折完延迟降了，却弄坏正常流程（主智能体手里有订单查询工具就自己答了，没去问物流专家要交货日期），而且这种破坏两次运行只出现一次，评估必须跑多次
  3. 工具定义超 30~50 个，工具选择开始退化——用延迟加载的工具搜索压住数量

分角色的真正理由：记忆边界 ·核心

上一节回答「组不组」，这一节回答「真要拆，按什么拆」。2026-10-26 补进的硅谷 101 那篇给了个更实用的答案。

Grok Bot 设计师郑芃的原话意思：人类团队分工是因为专业不同；Agent 团队分出一个「设计师 Bot」、一个「客户沟通 Bot」，关键不在专业能力，在记忆边界——

技能插件：共享

同一套工具、同一套技能，谁都能调，不重复装

记忆与偏好：各自独立

把同一类工作的上下文封在一个 Bot 里，避免「上下文污染」——另一个项目的特例跑来干扰眼前判断

判据反过来用：两件事需要记的东西高度重叠，就别拆成两个 Agent；记的东西完全不相干，才值得拆。角色是整理记忆的一种手段——一类工作长期交给同一个 Bot，它才攒得下经验，你也不用每次重讲背景。

同一篇给的两个反例：不是出错，是授权

  • Instinct 查航班条款时，直接把航班取消了，损失 300 美元
  • Muse 卖键盘时，未经同意让买家上门取货，收货差评
问题不在 Agent 的出错率，在用户根本没意识到自己授了多少权限。组队拆得越细，权限碎片越多，越需要一张「谁能动什么」的清单。

桑老哥直用

  • 给铁柱派活用启发式：「这图你有想法放开试，拿不准我们聊」好过「把这图做一下」——同一规律
  • 铁柱带 Subagent 干活时同样适用：鼓励式引导 + 验收点亮点，不用冷冰冰的命令 prompt
  • 认知锚：看到「多 Agent 平台」宣传先问一句——协作机制是什么？还是只是拉了个群？

前提与局限

  • 多 Agent 不是越多越好：每多一层协作就多一层延迟、费用和信息损耗（与 Agent工程规范误区三互证）
  • 「三步开工」的前提是 Leader 模型够强——Leader 弱，商量出来的共识也弱
  • 启发式管理提升的是输出的深度与创造性；要精确、要零出错的机械活，命令式更稳
