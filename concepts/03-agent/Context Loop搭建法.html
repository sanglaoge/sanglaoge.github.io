Context Loop搭建法

稳定 建条 2026-09-04 下次复核 2026-12-04

一句话说清楚

自进化 Agent 不玄——让 Agent 每天干活前，先读一遍你昨天随口留的反馈，照着改自己的规则文档。

循环工程管 Why、Agent自进化管 What，本词条管 How：一套可照抄的家用搭法。

样本案例：一泽Eze 的自进化信源日报系统

来源作者用豆包工作 + 飞书搭了一套每天自己变好的情报系统，全程可照抄。核心增量：把 Loop Engineering 从 Coding 场景拉到普通人日常办公。

表格管需求 → 文档管规则 → 定时采集出日报 → 群聊批注反馈回流 → 改规则再出报

自进化三条件（先拿这个判断） ·核心

一套系统能不能「自己变好」，三个硬条件缺一不可：

1人能顺手留反馈

发消息、写批注就行，不用专门填表

2Agent 有工具权限看到

这些反馈痕迹它得读得到

3Agent 能自己改长期记忆

Skill/规则文档，人也随时能上手共同编辑

三缺一，Loop 转不起来。只优化程序的叫代码循环，只改提示的叫人工迭代，都不是自进化。

系统骨架：六步阶梯（照抄能跑） ·核心

第1步
两张表

监测任务表 + 信息入口表。字段里最关键：证据边界、上次成功检查时间（增量游标）

第2步
需求入库

一句话需求拆成 MECE 任务 + 自动找信源入口；跑不通只标「待验证」

第3步
跑最小闭环

知识库三件：首页索引 + 日报规则 + 每日日报目录。先别加太多信源

第4步
定时推送

每日 Skill + 交互卡片 + 定时器；推送形态提前规定

第5步
反馈回流（关键）

每天抓新内容前，先整理前一天群聊+批注→反馈文档→按对象更新对应资产

第6步
推荐画像

加餐：命中监测任务=监测内容；未命中但符合画像=推荐内容

台阶越往上，系统越「活」——第 5 步是自进化的发动机

反馈回流怎么对应改：监测范围变了改任务表；信源变了改入口表；选材变了改规则；排版变了改模板。

采集三级阶梯（实测优先的 Agent 版）

从轻到重逐级尝试，上一层能稳定拿到就停：

一级
结构化入口

RSS / API / GitHub Releases

二级
直接读网页

读网页 / 轻量脚本

三级
浏览器模拟

Browser Use，登录态/强交互才用

越往上越重，能停在下层就别上台阶

验证标准：不是「网址打得开」，必须实际抓到标题 + 链接 + 发布时间才算跑通（实测优先）。

三个心法

反馈越顺手，Loop 越能持续

群聊留言、文档批注好过专门问卷。反馈门槛决定 Loop 生死——多一步「专门去填」就没人干

改文档 = 改行为

「每次任务会加载的上下文 = Agent 将遵循的任务指引」。想让 Agent 变，改它开工必读的那份文档就行——人改也行，Agent 自己改也行

看 Context 是 Context

Context 能提醒 Agent 读另一段 Context；来源形态多样（文件/群聊/文档/表格/批注），Agent 自己也是 Context 的输出者。换一种输入+输出 = 一套新工作流，骨架不用换

桑老哥直用

  • 每日推送升级图纸：现有的育儿知识 10:20 + 思维模型 11:00 推送是固定 Workflow（条件③有了）。按三条件补：推送末尾加一行「回复这条：有用/没用/想多看X」，铁柱每天推送前先读昨日回复再干活——就是最小反馈 Loop
  • 判断「自进化」产品真假：直接拿三条件套——反馈入口顺不顺手、它看不看得到、它改不改得了自己的规则
  • 采集阶梯用于选品情报订阅：sorftime 数据/API 属于第一级，别一上来就 Browser Use

前提与局限

  • 三条件缺任何一条，先补条件再搭系统——顺序不能反
  • 本条管 How，不管 Why/What：为什么值得做看循环工程，自进化的判定与反例看Agent自进化
  • 「改文档=改行为」依赖 Agent 每次开工真的加载那份文档——加载链路断了（没读到），改了也白改
  • 反馈回流是每天一次的节奏，不是实时——即时纠偏仍靠人
