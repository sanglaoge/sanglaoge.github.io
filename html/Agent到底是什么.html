01

什么是 Agent

要给 Agent 下个准确的定义，比想象中难。要么抛给你一串学术定义：感知、规划、记忆、行动，听起来都对，但落到工程里，还是不知道第一步该怎么做。

所以这篇文章不先追求一个完美定义。我们先把 Agent 和工作流的边界讲清楚。

下一步做什么，如果是代码提前写死的，那更像工作流；如果需要模型根据当前情况自己判断，那才更接近 Agent。

工作流 vs Agent

▲ 图解 1：工作流 vs Agent 决策路径对比

所以，判断一个系统是不是 Agent，关键不在于它有没有接大模型、有没有调用 API，而在于：任务推进过程中，那些无法提前写死的关键决策，是不是交给了模型。

核心原则

确定的交给代码，不确定的交给模型。模型负责判断，工程负责兜底。

Agent 的三大基础

真正落地时，最先要看明白的是三个基础部分：模型、工具、提示词。这三个东西单独看都不复杂，但一组合起来，问题就开始变多。

▲ 图解 2：Agent 三大基础

模型：不是越强越好

选模型的第一直觉是挑最强的。但没有哪个模型能在能力、延迟、成本上同时做到最好。选模型本质上是在做取舍。

三条原则
  • ① 不是所有任务都需要能力最强的模型
  • ② 先保效果，再压成本（先跑通再降配）
  • ③ 别让模型做确定性的事（参数校验/格式转换交给代码）

工具：设计的三道护栏

✗ 反模式

没权限直接返回空 → 模型以为"没填"

返回原始 JSON → 模型抓错重点

工具全平铺 → 模型选错

✓ 正确做法

标"受限"而非空值

整理成业务状态再返回

先分流再执行（Router→Executor→Composer）

铁律：行动类工具必须确认

发邮件、删数据、下订单、改合同——凡不可逆、有成本、超授权的操作，都要加一道确认。Agent 可以自主，但自主一定有边界。

提示词：确定 vs 探索

任务类型提示词怎么写例子
确定规则写清依据、步骤、动作、异常分支退款处理：每步具体到调哪个 API
探索型任务写清目标、工具、约束、停止条件旅行规划：不给固定步骤，给边界

Agent 常见设计模式

把模式拆成两条线来看：第一条线问"一个 Agent 内部怎么推进"，第二条线问"多个 Agent 怎么分工"。

▲ 图解 3：两条线 × 六种模式
类型不是越往多体走越高级。从单体到多体，增加的是复杂度，不是能力等级。能一个 Agent 完成的，就不要拆成三个。

实战：跑通一个最小 Agent

不添新概念，只做一件事：带你亲手跑通一个最小可用的 Agent。

场景：旅行规划助手

输入"未来三天的苏州旅程"，它自己查天气、搜景点，最后生成一份三天行程。

为什么这个场景适合 Agent

关键在于，天气不是终点，而是约束。查到某天下雨，就要把露天景点挪走；排完发现博物馆周一闭馆，又要回头调整。下一步调什么，取决于上一步查到了什么——这正是 ReAct 适合的场景。

Agent 的五个组成部分

部分作用
大脑LLM，负责每一轮的推理
工具查天气 / 搜景点 / 模拟订酒店
提示词告诉它能用哪些工具、按什么规则推进
循环想→动→看→再想，直到行程排好
停止条件最多 12 轮；有成本操作先问人

ReAct 循环的核心格式

# 每一轮的输出格式
Thought: 当前掌握了什么、还缺什么、下一步做什么
Action: 工具名[参数]

# 工具执行后
Observation: 工具返回的结果

# 循环直到
Action: Finish[完整的三天行程规划]

确认机制：订酒店前必须停

查天气、搜景点是数据类工具，结果不理想可以重查，允许自主调用。但订酒店是行动类工具，可能产生真实成本，一旦执行就不容易撤回。

铁律

凡不可逆、有代价的操作，就该让用户确认后再执行。Agent 可以自己查资料、调整方案，但不能替用户花钱做决定。

05

总结

说到最后，还是那句话：优先找最简单的方案，只在真正需要时才增加复杂度。

Agent 很容易让人兴奋，但最后能不能跑稳，往往不取决于架构名字有多好听，而取决于几个很朴素的问题：

  • ① 目标有没有说清楚？
  • ② 工具边界有没有设计好？
  • ③ 哪些地方该让模型判断，哪些地方该交给代码？
  • ④ 有代价的动作，有没有让人确认？

这些问题想清楚了，一个简单的单体 Agent 也能把问题解决。想不清楚，再复杂的架构也只是把问题放大。
